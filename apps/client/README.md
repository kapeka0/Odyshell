<h1 align="center">Odyshell Client</h1>

<p align="center"><strong>The owner-controlled connection from a Linux Machine to Odyshell.</strong></p>

The Client maintains an authenticated outbound connection to the Odyshell Server. It exposes no
inbound port and gives Agents no SSH credential, VPN route, or direct private-network access.

## Enrollment

Install the Machine CLI as the dedicated Linux user that should execute Commands:

```bash
npm install --global @odyshell/cli
```

Register the Agent first. Then run the `ods up` command generated by **Add Machine** in the
dashboard:

```bash
ods --server https://api.example.com up \
  --token <single-use-token> \
  --name production-api \
  --agent-id <agent-id>
```

Enrollment creates an Ed25519 Machine identity and a Task Local Policy bound to the sovereign
Organization ID and selected Agent. Missing Organization identity, invalid Agent ID, non-Linux
host, malformed existing configuration, or mismatched Server fails closed. The one-time token is
never stored.

## Local Policy

The initial Profile allows:

- exactly one Agent;
- one concurrent Task and one concurrent Command;
- Tasks up to one hour;
- Commands up to ten minutes;
- up to 1 MiB of transient output;
- optional remote human approval.

The Server may grant less authority but cannot widen these limits. Commands are arbitrary,
non-interactive shell text. They may specify an absolute working directory, but never caller
environment variables or standard input.

Commands run directly as the Client's Linux user. There is no sandbox, rollback, sudo setup, or
command filter. Use a dedicated user without root, sudo, or Docker access. Grant that user only the
files, credentials, network, and services the Agent needs.

## Profiles and service

Every named Profile has a separate Machine key, Local Policy, state directory, and systemd user
service:

```bash
ods profiles ls
ods client status --profile default
ods client doctor --profile default
ods down --profile default
ods up --profile default
ods profiles remove default
```

The Client keeps output bounded, journals Task/Command lifecycle for reconnect reconciliation,
rejects replay and identity mismatches, and stops accepting new work while disconnected. A
connected Client receives cancellation and revocation immediately; a partition is still bounded
by the already-authorized local timeout.

`ods client update` accepts only a compatible patch release, verifies npm SHA-512 integrity,
restarts the systemd service, and restores the prior package when activation fails.
