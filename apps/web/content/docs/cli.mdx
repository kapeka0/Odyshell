`ods` uses Odyshell Cloud by default. Select a self-hosted Server with `--server` or
`ODYSHELL_SERVER_URL`. Add `--json` when an agent needs structured output.

## Install

Requires Node.js 24 or newer:

```npm
npm install --global @odyshell/cli
```

## Common commands

```bash
ods login
ods status
ods machines
ods ping my-machine
ods exec my-machine -- uname -a
ods shell --purpose "Inspect the user environment" my-machine "pwd && id"
ods fs list my-machine .
ods fs read my-machine README.md
ods docker logs my-machine api --tail 100
ods audit
```

## What `ods login` authorizes

`ods login` authenticates the human-facing CLI to one Workspace. It lets that CLI discover and
manage Workspace resources, request Sessions, and create enrollment or Agent credentials when the
member's role permits it. The browser identity and Clerk credentials remain in the web app; the CLI
receives an expiring Workspace credential.

Machine enrollment is a different identity flow. A target machine does not need `ods login`: run
the single-use `ods up` command generated by an authenticated Workspace member. The Client exchanges
that enrollment token for its own machine identity and then reconnects with that identity.

## Client lifecycle

- `ods up` verifies Server reachability, enrolls when needed, and starts the background Client on
  Linux, macOS, or Windows.
- `ods down` stops that Client.
- `ods client doctor` checks the installed version, protocol, prerequisites, service, and configuration.
- `ods client update` verifies and installs the latest compatible patch, restarts the service, and
  restores the previous version if activation fails.
- `ods client enroll` creates a machine identity explicitly.
- `ods client start` runs the Client in the foreground.
- `ods profiles ls` lists local Profiles and their service state.
- `ods profiles status <name>` inspects one Profile.
- `ods profiles configure <name> --allow-sudo` explicitly permits passwordless sudo for an
  installed Linux service.
- `ods profiles configure <name> --deny-sudo` restores that service's `NoNewPrivileges` boundary.
- `ods profiles remove <name>` stops a Profile and deletes its local identity.
- `ods reset --yes` signs out and removes every local Profile, including legacy identities.

The sudo setting controls the installed Linux systemd service. A foreground `ods client start`
process keeps the operating-system user's real authority and detects effective `sudo -n` so
approvals can warn even when the Profile setting is disabled. Odyshell does not claim equivalent
privilege-escalation enforcement on macOS or Windows.

Use `--profile <name>` with `ods up`, `ods down`, or `ods client status` when one host connects to
several Workspaces or Servers. Profiles are isolated and can run simultaneously. The default name
is `default`; `--profile` and `--config` cannot be combined.

Profile commands also support `--json` for automation:

```bash
ods --json profiles ls
```

Local removal does not delete Cloud machine records. They remain offline until removed from the
dashboard.

## Sessions

High-level operation commands request a Session derived from the exact operation. If no matching
policy exists, the CLI prints an approval URL and waits. The Session Credential is claimed once,
used for the operation and revoked when the command finishes.

`ods shell --purpose <purpose> [--title <title>] <machine> <command>` requests an explicit Host
Shell Session, generates a Task Run identifier, waits for human approval, runs one native command,
and explicitly completes the Session with the command outcome.
`--purpose` is required and describes the goal shown before approval. Pass the complete command as
one quoted argument. Its task budget defaults to one hour; `--ttl` can shorten it or request a
longer justified duration up to 24 hours. Host Shell starts in the Client user's Home and has no
sandbox or isolation.
Its process receives an allowlisted base environment rather than every Client variable; explicit
values last for one Operation, although a POSIX login shell can load user startup files. An abrupt
Client crash can leave a detached POSIX command running; the result is reconciled as unknown.
Prefer `ods exec <machine> <program> [args...]` when an exact program and argument list is
sufficient.

## Agent integrations

`ods mcp` starts the local MCP server over stdio. After `ods login`, it creates one persistent
local Agent identity. That Agent requests temporary Sessions; the user approves the machine,
typed operation and duration in the browser.

The MCP exposes machine discovery and ping, Session request/status/completion, typed execution and
the verified timeline. It cannot enroll machines, manage people, expose credentials, or use
administrator commands.
