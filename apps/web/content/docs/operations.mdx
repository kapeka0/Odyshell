## Capability reference

| Capability | Purpose |
| --- | --- |
| `process.exec` | Run one executable with an argument array |
| `process.shell` | Run explicit shell text |
| `fs.stat` | Inspect file metadata |
| `fs.list` | List a directory |
| `fs.search` | Search filenames below the workspace |
| `fs.read` | Read a file |
| `fs.write` | Write a file |
| `fs.mkdir` | Create a directory |
| `fs.remove` | Remove a file or directory |
| `docker.logs` | Read logs from a Docker container |

Filesystem paths can be relative to the machine's configured root or absolute on a host profile.
An Agent can request an exact path restriction so that approving one file does not grant its
parent directory. A Session without filesystem path restrictions grants its selected filesystem
capabilities across the host as the Client's operating-system user. Docker profiles do not expose
absolute host paths.

Restricted Agent Sessions fail closed:

- filesystem path restrictions, when present, allow only the exact path or approved descendant
  tree;
- `process.exec` requires an exact executable, argument array, and working-directory rule;
- `docker.logs` requires an exact container name;
- `process.shell` is an explicit broad capability and is never autoapproved.

The Server checks the selected machine scope, and the Client enforces the same restrictions again
before executing locally.

## Process execution

Prefer structured execution:

```bash
ods exec my-machine -- git status --short
```

Agents can request exact `process.exec` operations through MCP or the API. The dashboard's manual
Session form stays intent-based and does not ask members to encode exact program arguments.

Use `process.shell` only when the task genuinely needs several dependent commands, pipelines, or
shell syntax. Shell access permits multiple independent Operations for the Session duration; it
does not create a persistent terminal or preserve `cd` and environment changes between commands.
The Agent receives stdout and stderr live and may issue more Operations inside the same Session.
The dashboard records sanitized commands and exit status, not output. Operations run with the
permissions of the operating-system user running the Client. Linux Profiles block privilege
escalation unless their machine owner explicitly enables passwordless sudo. When enabled,
`process.exec` can approve an exact sudo command and `process.shell` can run sudo for the Session
duration; approval surfaces warn about possible root access.

## Docker

`docker.logs` reads container logs through the host runner. Access to the Docker daemon is highly
privileged and should only be granted to the dedicated Client user when required.

The optional Docker runner executes supported work in an isolated container with networking
disabled. It is a separate execution profile, not a requirement for using Odyshell.
