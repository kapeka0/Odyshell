---
title: MCP
description: Let an MCP-compatible agent request temporary access to a private machine.
---

Odyshell exposes the same approval-based tools through a remote OAuth connection and through the
local `ods mcp` process. An agent has a persistent identity but no machine authority until a member
approves a temporary Session.

## Remote MCP

On a Server with Clerk OAuth enabled, add its MCP resource to an MCP-compatible client:

```text
https://mcp.example.com/mcp
```

The client opens Clerk in the browser. Sign in and approve access to your Odyshell account. If your
account can access more than one Workspace, use the Workspace-specific URL shown by Odyshell:

```text
https://mcp.example.com/mcp/<workspace-id>
```

The consent screen also selects one Organization. Odyshell binds the installation to that exact
Organization; membership in another Organization does not grant access to its Workspace.

OAuth identifies the MCP installation. It does not authorize machine Operations. Odyshell creates
or restores one persistent Agent for that installation, then requires a scoped Session for every
task. Approved Sessions are bound to the installation in PostgreSQL, so Server restarts do not lose
them and no Session Credential is returned to the model.

## Local MCP

Use the local process when a client supports stdio MCP or when you self-host without Clerk OAuth.

### Install

```npm
npm install --global @odyshell/cli
```

### Configure an agent

First sign in:

```bash
ods login
```

Then add:

```json
{
  "mcpServers": {
    "odyshell": {
      "command": "ods",
      "args": ["mcp"]
    }
  }
}
```

The process uses the existing local `ods` configuration. Its identity is saved locally. A claimed
Session Credential stays in MCP memory and is never returned in a tool result.
Local `ods mcp` reuses only Sessions claimed by that same running process, after revalidating that
the Session is active, unexpired, ready, and covers every requested Operation. It never saves the
Session Credential. An MCP-host or `ods mcp` restart can still recover pending, unclaimed requests,
but restarting `ods mcp` requires a new Session request and approval before using authority that a
previous process had already claimed.

Remote MCP keeps its installation-bound Session grant in PostgreSQL. That persistent binding lets
the same installation reuse compatible ready authority across stateless requests and Server
restarts without returning the credential to the model.

## Request an operation

The approval-based workflow exposes eight tools:

1. `machines_list` finds the target machine and reports its description, platform, architecture,
   runner, effective capabilities, and privilege-escalation policy.
2. `machine_ping` checks the complete connection path.
3. `sessions_list` returns pending requests and active Sessions. Call it before requesting access
   so existing ready authority can be reused after an interrupted response, a new chat, or another
   step in the same Agent task. History is optional. A local process restart does not preserve a
   claimed Session Credential; remote installation grants do survive Server restarts.
4. `session_request` accepts an optional short title, optional purpose, and either exact typed
   Operations or explicit broad Host Shell authority. When the title is omitted, Odyshell uses the
   purpose or derives a short title from the requested authority. A Host Shell request identifies
   its machine, objective, duration, and capability without approving an advance command list.
   Local MCP reuses compatible authority claimed in the current process; remote MCP reuses a
   compatible ready Session bound to the persistent installation. Otherwise the tool returns an
   approval URL for new authority.
5. `session_status` checks the decision and privately binds the approved Session.
6. `operation_execute` executes only an approved operation and requires an explicit UUIDv4
   `idempotencyKey`. Generate a fresh UUID for each logical Operation, and reuse that exact UUID only
   when retrying the same call. A later call uses a new UUID even when its Session, action, timeout,
   or JSON-RPC request ID matches an earlier call. The UUID is independent of command text,
   arguments, file content, environment values, and standard input, so retained idempotency
   metadata cannot act as a content dictionary oracle. If the requested timeout exceeds the
   Session lifetime remaining, Odyshell safely reduces it instead of requiring another tool call.
7. `session_complete` closes access when no Operation is active and records the agent-reported outcome.
8. `timeline_list` reads the verified Session timeline.

When approval is required, the agent shows the URL returned by `session_request` as a clickable
link and waits. Open it to review the exact typed Operations or broad Host Shell authority, then
approve or deny the request. The Sessions page shows the pending request immediately, then replaces
it with the active Session after approval and one-time claim. Its pending row opens the same review
URL shown by the agent. The agent calls `session_status` and continues only if
Odyshell grants the Session and the Client reports it ready.
The Agent can select an explicit compatible Session from `sessions_list` when it is bound to the
current local process or remote installation. Calling `session_request` performs the same
transport-appropriate compatibility check before creating a duplicate approval request.

Odyshell returns a `nextAction` after both the request and status checks. Agents should follow it
instead of asking the member to repeat an approval. A ready status points to `operation_execute`;
an opening status points back to `session_status` while the Client finishes opening the Session.

Agents should inspect `machines_list` before choosing commands. Machine, Session, and status
results expose the machine description, allowlisted platform, architecture, runner, effective
capabilities, default shell, and whether sudo is locally allowed so
a Windows machine does not receive Linux-only commands such as `df -h`.
On Linux this reports effective runtime access: an installed service enforces its disabled setting
with `NoNewPrivileges`, while a foreground Client probes `sudo -n` because it has no equivalent
service boundary.
Before requesting a sudo command, the Agent must disclose intended root access in the Session title
or purpose so the approval is unambiguous.
If an executable is unavailable, `operation_execute` directs the Agent back to `machines_list`
instead of encouraging another platform guess.

Each structured Operation determines its capability and restriction automatically. Scopes for the
same machine are combined without broadening their exact restrictions. Filesystem Operations use
an exact path relative to the Client user's Home or an absolute host path, `process.exec` uses an
exact executable and arguments, and `docker.logs` uses an exact container. Absolute host paths
require a host Profile; Docker Profiles use their Docker-specific mount source.
Approval codes expire, are single-use and are bound to their Workspace.

If combining filesystem operations would authorize a capability on a path that was not requested,
Odyshell rejects the group. Request those operations in separate Sessions.

The Server validates Session identity, machine, capability, path and expiry on every Operation.
The Client applies its local policy independently.

Agents should prefer native filesystem and Docker Operations or `process.exec`. They can request
`host.shell` for multi-step work where the next command depends on stdout or stderr from the
previous one. Host Shell authority is broad, temporary, never autoapproved or delegated, and
bounded by the machine's Local Policy. Each command is a separate Operation that starts in the
Client user's Home by default; there is no persistent terminal, PTY, sandbox, isolation, or shell
state across commands. A per-command working directory does not narrow Host Shell authority.
Commands run with everything available to the operating-system user running the Client, and their
changes may persist after the Session ends. The command inherits an allowlisted base environment;
explicit environment values apply only to that Operation and are never persisted, while a POSIX
login shell can still load user startup files. Graceful cancellation stops the process group, but an
abrupt Client crash can leave a detached POSIX command running; the result is reconciled as
unknown.

## Client-side blocks

An MCP host may apply its own plan, safety or tool-availability controls before a call reaches
Odyshell. If the host reports that a tool was blocked and no Operation appears in the Session
Timeline, the machine and Session are not the cause: Odyshell never received the call. Continue in
a host that exposes `session_status` and `operation_execute`, or use the local `ods mcp` connection.
Odyshell does not weaken operation annotations to bypass a host's safety controls.
