title: Machines
description: Enroll a machine, choose its local capabilities, and keep its Client connected.

Install the CLI on the target machine with Node.js 24 or newer:

```npm
npm install --global @odyshell/cli
```

## Enroll from Odyshell Cloud

Open **Machines**, select **Add**, and configure:

- a machine name;
- the capabilities the machine will accept.

Odyshell generates an `ods up` command containing a single-use enrollment token. Run it on the
target machine. The token expires after ten minutes and cannot be replayed.
The member who created the command receives a dashboard notification when that machine enrolls.

After it connects, open its actions and select **Edit** to change its name, add a short description,
or reduce its effective capabilities. Descriptions help agents identify the correct machine through
`machines_list` and appear beneath the machine name in the dashboard.

`ods up` installs and starts a restartable user service on Linux, macOS, and Windows. After
enrollment, use:

```bash
ods client status
ods down
ods up
```

Linux uses a systemd user service, macOS uses a LaunchAgent, and Windows uses a per-user Task
Scheduler task with a native no-console launcher. The terminal can be closed after `ods up`; none
require administrator privileges.

If a machine was removed in Cloud but its local Profile still exists, create a new machine command
and run it with the same `--profile`. Odyshell replaces the revoked identity and restarts the
background Client. It refuses to replace an identity that is still active, and the new token is not
consumed by that refusal.

## Local policy

Relative paths resolve from the directory where the Client Profile was first enrolled. Restricted
Sessions may also request an exact absolute path or process working directory on a host profile;
that path is shown explicitly for approval. Docker profiles remain limited to their mounted
directory and cannot use absolute host paths.
Capabilities are default-deny and comma-separated:

```bash
--allow 'process.exec,fs.stat,fs.list,fs.search,fs.read'
```

The capabilities selected during enrollment remain the Client Local Policy and cannot be expanded
from the web. Machine editing can only choose a Server-side subset of that local maximum. New
Sessions must pass both boundaries; an existing immutable Session keeps its approved scope until
it expires or is revoked.

Linux Profiles also block privilege escalation by default. To let approved process Sessions use
passwordless sudo, the machine owner must opt in locally:

```bash
ods profiles configure default --allow-sudo
```

The command verifies `sudo -n`, persists the setting, and restarts only that Profile. Restore the
default with `ods profiles configure default --deny-sudo`. Machine details and MCP discovery report
the current policy. Typed filesystem operations never gain sudo automatically.

## Client Profiles

A host can run several named Client Profiles at the same time. Each Profile keeps an independent
Server, Workspace, machine identity, relative-path base, capabilities, state directory, and background
service:

```bash
ods --server https://personal.example up --profile personal <enrollment-options>
ods --server https://company.example up --profile company <enrollment-options>

ods --server https://company.example client status --profile company
ods --server https://company.example down --profile company
ods profiles ls
```

Omitting `--profile` selects `default`. The first use imports the previous single Client
configuration into that Profile. If both identities already exist, Odyshell stops and asks you to
resolve the conflict instead of choosing or overwriting one. `--config` remains available for an
explicit path and cannot be combined with `--profile`.

Do not reuse or copy a Client configuration between machines.

Remove one local identity with `ods profiles remove <name>`. To sign out and remove every
local Profile from a host, run `ods reset --yes`. These commands leave Cloud machine records
offline until they are removed from the dashboard.
